**Date:** 2026-05-11

**JAR md5 deployed:** `deb0b5724b83099e279ace65cdf53afd` (cloud-plugin-hypervisor-kvm-4.24.1.26-SNAPSHOT.jar)

## Fix description

Extend the OVN VIF-driver post-plug stamp paths to write
`external_ids:ovn-installed=true` on the OVS Interface row alongside
the existing `iface-id=lsp-<uuid>` and `iface-status=active` stamps.
The change is a single-call `ovs-vsctl set` across three locations,
keeping the cost identical to the legacy single-key stamp:

| Driver / hook | File | Why it matters |
|---|---|---|
| TAP / OvnVifDriver | `plugins/hypervisors/kvm/src/main/java/com/cloud/hypervisor/kvm/resource/OvnVifDriver.java` (`applyPostPlugTunables`) | Default OVN driver for non-HW-offload tier NICs. Stamp runs on fresh plug AND on post-migrate dispatch. |
| vDPA / LibvirtComputingResource | `plugins/hypervisors/kvm/src/main/java/com/cloud/hypervisor/kvm/resource/LibvirtComputingResource.java` (`applyVdpaPostPlugTunables`) | Cycles iface-status from `inactive` (set at plug) to `active` after the VM reaches running state (Bug 16/17 deferred-active pattern). Now also stamps `ovn-installed=true` in the same `ovs-vsctl set` call. |
| VF passthrough / OvnVfPassthroughVifDriver | `plugins/hypervisors/kvm/src/main/java/com/cloud/hypervisor/kvm/resource/OvnVfPassthroughVifDriver.java` (`attachRepresentorToBrInt`) | HW-offload SR-IOV tier; the representor must be stamped at plug time because the VM uses PCI passthrough and there is no later tap-rename hook. |

### Why the flag is load-bearing on post-migrate (and why the audit was correct to flag it)

The `external_ids:ovn-installed` flag is the per-Interface contract that
`ovn-controller` normally sets after claiming the matching `Port_Binding`
row in OVN_Southbound. The contract works automatically in the
fresh-plug case: plug -> ovn-controller observes a new Interface row
with `iface-id=lsp-...` -> claim sequence runs -> controller writes
`ovn-installed=true`. The OpenFlow ingress action depends on this flag
being present.

On live-migration, the chassis owns the same `Port_Binding` from before
the migrate (only the chassis-binding column changes; the iface-id is
unchanged). `ovn-controller` on the destination chassis observes a
row whose iface-id is already known and does NOT re-trigger the bind
sequence. The pre-Bug-26 agent-side post-migrate stamp dispatched by
`VirtualMachineManagerImpl.dispatchPostMigrateOvnStamp` only wrote
`iface-id` and `iface-status` — the `ovn-installed` column stayed at
its pre-migrate value. For an Interface row that had been claimed and
flagged previously the row carried `ovn-installed=true` already, but
for vDPA representors whose representor name changed between source
and destination chassis (mlx5 e-switch picks different VF allocations
per host) the destination row was a freshly-discovered Interface
with iface-id stamped post-libvirt-up but no ovn-installed flag —
producing the symptom captured in the original Bug 26 audit
(`ovn-installed-ts` present, `ovn-installed="true"` absent).

Stamping `ovn-installed=true` from the agent shortcuts the controller's
claim sequence: the row already advertises that the chassis considers
the port bound, and `ovn-controller` keeps the flag in subsequent
re-syncs unless its own bind decision contradicts it. On the fresh
plug path the agent and the controller race to set the same value,
which is harmless (both want `true`).

## Why this fix is idempotent on the fresh-plug path

On fresh plug:
- The OVN VIF driver runs `ovs-vsctl set Interface <rep> external_ids:iface-id=... external_ids:iface-status=active external_ids:ovn-installed=true`.
- `ovn-controller` observes the new Interface row, runs its bind sequence (because `iface-id` matches an unbound `Logical_Switch_Port.name`), and writes `external_ids:ovn-installed=true` itself.
- Both writes land on the same column with the same value — idempotent. `ovn-controller` does not unset a flag the agent already wrote when the bind decision agrees with the agent's intent.

On migrate destination:
- The agent runs the same stamp via the post-migrate command wrapper.
- `ovn-controller` observes a row whose iface-id is already claimed by another chassis (the migrate source) and re-claims via the chassis-binding update path — but the bind decision does NOT re-fire the per-Interface flag write because the iface-id was already known.
- The agent-side stamp is therefore the only path that flips the flag on the destination; without it the row carries iface-id but no ovn-installed flag.

## Lessons

- **OVN columns are bidirectional contracts.** The `ovn-installed` column is owned by `ovn-controller` in normal flow, but agent-side writes are honoured when they don't contradict controller intent. Stamping from both sides on the fresh-plug path is the right idempotent pattern.
- **Live-migration is the worst case for "ovn-controller owns the column".** The bind-sequence-skipping logic that makes migration fast also skips the column write the agent depends on. Agent-side fallback is required.
- **Three drivers, one contract.** Fixing only one of the three VIF drivers would leave the other two tiers broken in the same way. The fix had to land in all three (TAP, vDPA, VF passthrough) in a single commit to keep the contract consistent.
