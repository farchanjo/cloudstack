# Bug 20 + Bug 21 — DEFERRED: systemd configuration changes live outside the CloudStack source tree

**Date:** 2026-05-11
**Status:** DEFERRED
**Severity:** MEDIUM (operational; not blocking platform functionality)
**Original audits:**
- `2026-05-11-bug-20-ovs-setup-frr-restart-hang.md` (ovs-setup.service reverse-dep hang)
- `2026-05-11-bug-21-trevor-agent-silent-failure.md` (ovn-host PID-file stale state)

---

## Why DEFERRED

Both bugs need configuration changes to systemd / shell-script artifacts
that do **not** live in the `~/dev/cloudstack` source tree. Per the
project's strict code-ownership rule (`~/dev/dc/CLAUDE.md`,
"CLOUDSTACK CODE OWNERSHIP" section), source edits land **only** at
the local workstation under `~/dev/cloudstack`. Patching production
hosts without a corresponding source-tree mirror would diverge prod
state from the canonical source, and the next external-tool reconcile
(Ansible, deb post-install, etc.) would revert the change.

### Bug 20 — `/usr/local/bin/ovs-setup.sh` line ~290 + `/etc/systemd/system/ovs-setup.service`

`/usr/local/bin/ovs-setup.sh` header:

```bash
#!/bin/bash
# /usr/local/bin/ovs-setup.sh
# Managed by Ansible role ovs_kernel_dataplane — DO NOT EDIT MANUALLY
# Host: aragog (slytherin)
# Generated: 2026-05-07T15:42:42Z
```

The script and its companion `ovs-setup.service` unit are produced by
an **external Ansible role** (`ovs_kernel_dataplane`) outside this
repository. They are NOT installed by any `cloudstack-agent` deb
post-install hook and they are NOT version-tracked in
`~/dev/cloudstack`. Searches:

```
find ~/dev/cloudstack -name 'ovs-setup.sh' -not -path '*/target/*' -not -path '*/.git/*'
# -> no results

find ~/dev/cloudstack -name 'ovs-setup.service' -not -path '*/target/*' -not -path '*/.git/*'
# -> no results
```

The correct fix surface is the Ansible role definition (likely in a
separate ops repository). Patching the on-host files directly would
be undone on the next `ansible-playbook` run.

### Bug 21 — `/etc/systemd/system/ovn-host.service` (auto-generated from SysV)

`systemctl cat ovn-host` on trevor:

```
# /run/systemd/generator.late/ovn-host.service
# Automatically generated by systemd-sysv-generator
SourcePath=/etc/init.d/ovn-host
```

The `ovn-host.service` unit is **not a real systemd unit file**. It is
auto-generated by `systemd-sysv-generator(8)` from the `/etc/init.d/ovn-host`
LSB SysV-style init script shipped by the **upstream `ovn-host` Debian
package** (currently `ovn-host 26.03.2-1` on this cluster). Editing
`/run/systemd/generator.late/ovn-host.service` is meaningless — the
file is regenerated on every `systemctl daemon-reload`.

The correct fix surface is one of:
- A systemd unit drop-in under `/etc/systemd/system/ovn-host.service.d/override.conf` that adds `PIDFile=` and `ExecStartPre=-/bin/rm -f /var/run/ovn/ovn-controller.pid`. This is a host-local config artifact (not in CloudStack source).
- Upstream `ovn-host` package patch (lives in the OVN project, not CloudStack).
- An external Ansible role that materializes the drop-in (same class as Bug 20).

None of these paths land in the CloudStack source tree.

---

## Production state at time of audit (2026-05-11)

`cmk list hosts type=Routing` shows all 6 data nodes `Up + Enabled`.
Bug 20 and Bug 21 are not active failures right now; they are
*future failure modes* that surface on the next reboot or
manual `systemctl restart ovs-setup.service`. The manual remediations
documented in their respective audits are still applicable as
runbook entries:

- Bug 20: kill the stuck `systemctl try-restart frr` subprocess via `pkill -9`
  to unblock the host boot sequence.
- Bug 21: `pkill -9 ovn-controller && rm /var/run/ovn/ovn-controller.pid && systemctl reset-failed cloudstack-agent ovn-host && systemctl start cloudstack-agent ovn-host`.

---

## What is required to FIX

1. **For Bug 20**: locate the `ovs_kernel_dataplane` Ansible role definition
   (probably in an ops repository alongside the keepalived / ceph / BGP
   roles). Edit `ovs-setup.sh.j2` and `ovs-setup.service.j2` templates
   to either:
   - drop the `systemctl try-restart frr` line entirely AND remove
     `Before=frr.service` from the unit (preferred — eliminates the
     loop closure); OR
   - add `--no-block` to the `systemctl try-restart frr` invocation
     (one-line hotfix).
2. **For Bug 21**: either patch the upstream `ovn-host` package's
   `/etc/init.d/ovn-host` to handle stale pidfile, OR ship a systemd
   drop-in via the same Ansible role as `ovs_kernel_dataplane` (or
   a new ops role).
3. Land the changes in the ops repository, NOT in `~/dev/cloudstack`.
4. Re-run `ansible-playbook` against the 6 data nodes to materialize
   the new files.
5. Create a NEW audit file (`2026-05-11-bug-20-21-FIX.md` or similar)
   citing the ops-repo commit hash + production verification.

## Why this is DEFERRED rather than WONTFIX

The bugs remain real and warrant fixing. The defer reason is
"out-of-scope for the CloudStack source tree". Once the ops-repo
fix lands, the audit log gets a normal FIX entry — same pattern as
the FIXED rows for Bugs 14 / 14b / 16 / 17 / 18 / 19 / 22 (OBSOLETE) /
23 / 24 / 25 / 26.

The original Bug 20 + Bug 21 audit files remain OPEN per
append-only convention until a follow-up FIX audit cites the resolving
ops-repo commit + production verification.
