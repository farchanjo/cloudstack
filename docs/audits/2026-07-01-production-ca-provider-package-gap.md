# Production `cloudstack-management` package gap — `openbao-ca` never actually deployed

**Date:** 2026-07-01
**Status:** OPEN — dead DB config identified, no source/package change made
**Severity:** LOW (no live impact confirmed — see verification), but blocks the entire
`openbao-ca` rollout until the packaging gap is closed.
**Scope:** production LAX control nodes (voldemort/bellatrix/barty), `cloudstack-management`
Debian package and its relationship to `ca.framework.provider.plugin`.

---

## Summary

`ca.framework.provider.plugin` reads `openbao` in the production `configuration` table
(all `ca.plugin.openbao.*` settings — url, mount, sign/issue role, AppRole role-id +
secret-id — are also populated, dated 2026-06-27 23:04:47). This looked, at first read,
like `openbao-ca` was already the live CA provider. **It is not.** The installed
`cloudstack-management` package on all 3 control nodes is `4.24.1.18-20260425T183750~noble`
— last touched by `dpkg`/`apt` on **2026-04-25**, over two months before the
`ca.plugin.openbao.*` config rows were ever written, and containing zero `openbao-ca`
class or resource on disk (`find /usr/share/cloudstack-management -iname '*openbao*'`
returns nothing on all 3 nodes).

`CAManagerImpl` only assigns `configuredCaProvider` when
`caProviderMap.containsKey(CAProviderPlugin.value())` — see
`server/src/main/java/org/apache/cloudstack/ca/CAManagerImpl.java`. Since no
`openBaoCAProvider` Spring bean exists in the running JVM (the plugin JAR was never
packaged into this `.deb`), that key lookup always misses and the assignment never runs.
**`root-ca` remains the actual active provider** — the DB value is a harmless no-op,
written by an earlier session while staging config ahead of a deploy that hasn't
happened yet.

## Verification (read-only, all 3 control nodes unless noted)

1. `dpkg -l cloudstack-management` → `4.24.1.18-20260425T183750~noble`, `hi` (hold/installed,
   not upgradable pending — normal apt-hold-style pin).
2. `zgrep cloudstack-management /var/log/dpkg.log*` on voldemort → last `upgrade`/`configure`
   event is 2026-04-25 18:47:09 → `.18-20260425T183750~noble`. No install/upgrade/downgrade
   event since. The package has been static for 2+ months.
3. `find /usr/share/cloudstack-management -iname '*openbao*'` → empty on voldemort.
4. `cloudstack-management` service `ActiveEnterTimestamp` = 2026-06-29 05:04:14 UTC (a routine
   restart, unrelated to any CA change — no `openbao-ca` jar existed at that point either).
5. All 6 LAX hosts report `state: Up`, `resourcestate: Enabled` via `cmk list hosts` — no
   agent disconnects, no `CAManagerImpl`/`OpenBaoCAProvider` entries in
   `management-server.log` (only the unrelated, harmless
   `ConfigurationManagerImpl ... Did not find configuration [ca.plugin.openbao.*] in
   Config.java. Perhaps moved to ConfigDepot.` WARN lines — those fire for *any*
   `ConfigKey`-based setting queried through the legacy `listConfigurations` code path,
   openbao-specific or not; they are not evidence of a provider-selection failure).
6. Cross-checked against a live agent certificate (`aragog`, `/etc/cloudstack/agent/cloud.jks`):
   chain is `CN=aragog` → `CN=Slytherin CloudStack Issuing CA` → `CN=Slytherin Root CA,
   OU=EONF Infrastructure, O=EONF, C=US`, leaf issued 2026-06-28. This is fully explained by
   `root-ca`'s support for an **imported** (non-autogenerated) CA key pair —
   `ca.plugin.root.ca.certificate` / `ca.plugin.root.public.key` are both populated in the
   DB since **2026-03-05**, three months before any `openbao-ca` work started. No OpenBao
   involvement required to produce this chain.

## Why this matters

The full `openbao-ca` completeness + real-infra validation done on 2026-06-30 (see
`2026-06-30-openbao-ca-completeness-and-integration.md`) built and unit-tested the plugin
via a plain `mvn` checkout on **aragog** (`/root/cloudstack`, a KVM hypervisor/agent node —
not a management-server host) and live-validated the OpenBao side (`pki_cloudstack` mount,
`cloudstack-ca` AppRole) directly over HTTP. None of that touches the actual
`cloudstack-management` **package** that ships to voldemort/bellatrix/barty. Building a JAR
in a git checkout and installing a `.deb` on the control nodes are two different pipelines,
and only the second one matters for activation.

**Closing this gap requires the CloudStack package build/publish pipeline** (the one that
produced `4.24.1.18-20260425T183750~noble` and the custom `CloudStack_EONF` Pulp/Katello repo
referenced in `foreman/CLAUDE.md`) to pick up a version ≥ `4.24.1.26-SNAPSHOT` (this repo's
current `pom.xml` parent version, which already includes `plugins/ca/openbao-ca`) and publish
it. That pipeline lives outside this repo — not yet located or documented as part of this
audit.

## Recommendation

- **Do not flip `ca.framework.provider.plugin` back to `root` as a "fix"** — it is already
  functionally `root` (see verification above); the DB value is cosmetic drift, not a live
  misconfiguration. Correcting the DB row is optional hygiene, not a safety action.
- **Real next step**: locate and understand the `cloudstack-management` package build/publish
  pipeline (likely a separate repo, mirroring `config-mgmt`'s GitLab CI → Pulp/Katello
  pattern per `foreman/CLAUDE.md`'s `CloudStack_EONF` custom repo reference), get a version
  containing `openbao-ca` published there, then upgrade the 3 control nodes through the
  normal package-management path. Only *then* does a management-server restart + the staged
  `ca.plugin.openbao.*` config become meaningful.
- Not investigated in this audit: what CI/repo builds `cloudstack-management` `.deb`s, or why
  it stopped advancing after 2026-04-25.
