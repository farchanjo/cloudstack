# Bug 24 — FIX — VR non-HW-offload tier NIC plug dispatches via OVN-aware vif driver and fires post-plug stamp

**Date:** 2026-05-11
**Status:** FIXED
**Severity:** HIGH
**Fix commit:** `19fb6cfde4346a8b98e2463b72d2c0310938c815`
**Companion (audit-only original):** `2026-05-11-bug-24-vr-tier-tap-bridge-mis-assignment.md` (status moved OPEN → FIXED by this audit)

---

## Summary

The original audit (`2026-05-11-bug-24-vr-tier-tap-bridge-mis-assignment.md`)
identified that after the Bug 23 fix (`71dcc1a633`) restored the missing
tier-tap NIC in the libvirt domain XML, the NIC was still being plugged
incorrectly:

1. **Wrong bridge.** `<source bridge='br-bond'/>` instead of
   `<source bridge='br-int'/>`. Traffic for the tap-tier MAC never entered
   the OVN pipeline because vnet100 lived on the underlay bond.
2. **Wrong `iface-id` stamp.** OVS `external_ids:iface-id` carried the raw
   NIC UUID instead of `lsp-<uuid>`. Even if the NIC had been on `br-int`,
   `ovn-controller` would not have claimed the Port_Binding — exactly the
   Bug 14 pattern, recurring on the VR-side hot-plug path.

Both defects share a single upstream cause in
`LibvirtPlugNicCommandWrapper`: dispatch through the legacy
`getVifDriver(TrafficType, name)` selector, which falls back to
`BridgeVifDriver` for OVN-tagged NICs and never runs the post-plug
tunable that emits `lsp-<uuid>`.

This audit closes Bug 24 with a two-line source change in
`LibvirtPlugNicCommandWrapper.java`, mirroring the proven dispatch
contract used by `LibvirtStartCommandWrapper` (Bug 14 boot path) and
`LibvirtPrepareForMigrationCommandWrapper` (Bug 14b migration path).

---

## Root cause

`plugins/hypervisors/kvm/src/main/java/com/cloud/hypervisor/kvm/resource/wrapper/LibvirtPlugNicCommandWrapper.java`
(pre-fix line 66):

```java
final VifDriver vifDriver = libvirtComputingResource.getVifDriver(nic.getType(), nic.getName());
```

`LibvirtComputingResource.getVifDriver(TrafficType, String)` is the legacy
selector that keys only on the `TrafficType` enum (`Guest`, `Public`,
`Control`, `Management`, `Storage`). It does **not** consult `NicTO`
flags — `isHWOffloaded()`, vDPA queue count, OVN broker mode — and falls
back to `BridgeVifDriver` for the Guest traffic type in all OVN
deployments. `BridgeVifDriver` resolves the bridge name from
`AgentProperties.GUEST_NETWORK_DEVICE` (`br-bond` in this fork) and plugs
the tap there, never touching `br-int`.

`LibvirtStartCommandWrapper` (boot path) and
`LibvirtPrepareForMigrationCommandWrapper` (migration path, Bug 14b)
already dispatch through the newer `selectVifDriverForNic(nic)`, which
inspects the NicTO and selects `OvnVifDriver` / `OvnVdpaVifDriver` /
`OvnVfVifDriver` for OVN-tagged NICs. That selector also lays the ground
for the post-plug stamp — `applyOvnPostPlugTunables` rewrites
`external_ids:iface-id` from the raw NicTO UUID to `lsp-<uuid>` once
libvirt has spawned the tap, idempotent and a no-op on non-OVN NICs.

The hot-plug path in `LibvirtPlugNicCommandWrapper` was the last
remaining wrapper that still used the legacy selector and never invoked
the post-plug tunable. Bug 24 is the symptom; the dispatch regression
class is the same Bug 14 / Bug 14b pattern.

---

## Fix

Commit `19fb6cfde4346a8b98e2463b72d2c0310938c815` —
`fix(plugins/hypervisors/kvm): plug NIC via OVN-aware vif driver and post-plug stamp`

`LibvirtPlugNicCommandWrapper.java` diff (17 insertions, 1 deletion):

1. Replace the legacy selector

   ```java
   final VifDriver vifDriver = libvirtComputingResource.getVifDriver(nic.getType(), nic.getName());
   ```

   with the NicTO-aware selector

   ```java
   final VifDriver vifDriver = libvirtComputingResource.selectVifDriverForNic(nic);
   ```

   so `nic.isHWOffloaded()`/vDPA flags route the dispatch to
   `OvnVifDriver`, `OvnVdpaVifDriver`, or `OvnVfVifDriver` and the tap
   lands on `br-int` with the OVN virtualport block.

2. After `vm.attachDevice(interfaceDef.toString())`, invoke

   ```java
   libvirtComputingResource.applyOvnPostPlugTunables(vmName, new NicTO[]{nic});
   ```

   so the OVN post-plug stamp rewrites `external_ids:iface-id` to
   `lsp-<uuid>` and stamps `iface-status=active`. The helper is a no-op
   for non-OVN NICs (control NIC on `cloud0`, etc.).

Inline comments cite Bug 24 root cause, the Bug 14 pattern that the
stamp is mirroring, and the dispatch parity with `LibvirtStartCommandWrapper`
plus `LibvirtPrepareForMigrationCommandWrapper`.

### Acceptance gate

> ALL Guest tier `<source bridge>` = `br-int` AND ALL Guest tier `iface-id`
> = `lsp-<uuid>`.

Pass. Only one Guest tier NIC is on a bridge (the tier-tap); both
conditions hold. The other two Guest tiers (vDPA and SR-IOV hostdev) do
not have a tap on any OVS bridge — they program the host eSwitch
directly via the representor lifecycle, which is independent of this fix.

## Re-test directives

A follow-up audit MAY reopen Bug 24 only if either of the following
conditions is observed:

1. A multi-tier VPC VR boots (or has a tier hot-plugged via
   `restartVPC cleanup=true` or `addNetworkToVpc`) with at least one
   non-HW-offload tier and the resulting libvirt XML shows
   `<source bridge='br-bond'/>` for that tier on a hypervisor running
   commit `19fb6cfde4` or later. Cite the offending host + VR UUID +
   `virsh dumpxml` excerpt + JAR md5.
2. OVS `external_ids:iface-id` for that tier's tap stays as the raw NIC
   UUID after the VR has been Running for at least 60 seconds. Cite the
   `ovs-vsctl --columns=name,external_ids list Interface <vnet>` output
   and the corresponding `<parameters interfaceid='...'/>` from the
   libvirt XML.

Any other Bug-24-flavored symptom on a hypervisor running an earlier
commit is drift on that host, not a regression — fix by redeploying
the agent JAR.
